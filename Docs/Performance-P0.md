# P0：先把卡顿原因和实战基准测准

2026-11-01 已完成卡顿归因、采集入口修正及长实战复测。改动位于开发专用性能工具，正常战斗逻辑、地图和数值保持原配置。本轮不是“所有游戏卡顿已消除”的结论。

## 归因

- 原 276.09 ms 帧有约 250.27 ms 的主线程等待，渲染线程约 290.25 ms，GPU 实际工作约 6.37 ms。不能将它全算成战斗计算或网络开销。
- 新 trace 复现了最长约 309.75 ms 的同步着色器等待；测试截图的 PNG 压缩约 207.60 ms，读回刷新约 34.57 ms，纹理平台数据准备约 148.91 ms。这些计时有并行或嵌套，不能相加。
- 原始 276 ms 帧没有逐函数 trace，因此这里只确认其等待组成，并用新 trace 解释同一启动流程的冷启动成本，没有声称重建了原帧完整调用栈。
- 另有真实战斗中的对象池取用与临时创建峰值。例如原房主第二轮的 95.07 ms 帧包含 PoolAcquire 37.93 ms、ActorSpawning 21.56 ms，留作 P1 的优化目标。

## 采集入口修正

`Source/ai/Private/Debug/RogueRealBattleCapture.cpp` 现在先准备至少 5 秒，非阻塞等待着色器、资产、管线预编译与异步加载队列连续 2 秒为空，才恢复正式刷怪。没有在采样中调用强制编译完成、渲染刷新或 GC。

双进程工具为两端增加独立 QA 文件同步：两端均就绪才开始战斗。此同步只用于本机性能测试，不改变正常联机准备流程。战斗开始后，工具默认至少预热 8 秒，再次确认队列稳定后进入 CSV；之后的坏帧和新任务全部保留。

预热期间不再截图，避免读回和压缩干扰临近帧。CSV 新增实际帧号、战斗经过时间和各类待处理计数，trace 增加准备结束、战斗开始、采集开始及结束标记。

启动脚本验证 CSV 与结果文件，不能把进程退出码 0 当作采集成功。普通 41 级构筑在预热结束前阵亡的试跑被正确拒绝，未进入长样本统计。

## 编辑器构建限制

本机 UE 5.5 的 `Engine/Source/Runtime/RHI/Private/PipelineStateCache.cpp` 中，`IsPSOPrecachingEnabled()` 在 `WITH_EDITOR` 分支直接返回 false。实测为 0，UnrealEditor.exe 加 `-game` 也一样。单改 `r.PSOPrecaching` 无法绕过，本轮没有修改引擎。

当前队列清空不保证未来所有材质和特效已经首用。本轮部分样本中仍观察到新的着色器任务，原始数据完整记录，不能把这批数据称为“完全无编译稳态”。后续烘焙的 Game 构建需要单独验证预缓存与首次出现卡顿。
